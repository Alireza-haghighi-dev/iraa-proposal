## 12. Detailed technical implementation method

### Problem-solving logic

The assistant prepares an assessment record for each submission and fills it with three ranked lists: earlier stored submissions that resemble the new one [R1], existing solution examples from whichever sources are registered [R2], and external patents found with an approved query [R4]. The assessor reads the evidence, completes the assessment fields and approves the record; only that approval can make an outcome final [R3]. The technical work therefore has two parts with different success conditions. The three retrieval tasks are measured on judged test sets and can turn out well or badly; the approval rule is a property of the record service that either holds on every path or does not.

R1 and R2 are the same retrieval problem applied to different collections, so one retrieval service ranks every registered corpus with the same set of configurations, and each corpus has its own lexical and vector index [AD-01]. Which configuration the prototype uses is decided by evaluation, not fixed in advance: no method leads across public benchmarks, and no benchmark of need or challenge submissions was found in our searches [AD-02, CLM-025, CLM-026]. The configuration set runs from a naive date-ordered list to BM25, three dense encoders, two fusion methods and an optional re-ranker, so that the evaluation can show whether the added components are worth their cost on this kind of text.

### What the project controls and what it does not

The project controls the design, the code, the configuration set, the evaluation protocol, the judging guide, the substitute test collections it builds, and the reference environment on which timing is measured. It does not control whether the sponsor releases stored submissions [ISS-002], which solution-example sources count for R2 and whether any is available [ISS-003, ISS-037], whether submission text may leave the controlled environment [ISS-033, ISS-009], which patent service may be used [ISS-040], the language of submissions [ISS-007], or whether assessors can take part in judging [ISS-012]. Each of these has a defined branch in the method, so that work continues whatever the answer: file import with a substitute schema if no export is released, evaluation on substitute data reported separately as Track P if no sponsor data is available, an assessor-approved query before any external search while disclosure is not authorized, manual entry of assessor-run searches if no patent service grants access, and project judges if assessors are not available. Results on substitute data are reported as such and are never presented as performance on sponsor submissions [ISS-028, CLM-045].

### Requirements, constraints and scope

The functions built are those of the essential set approved for this project: import and normalization, R1 and R2 retrieval with evidence passages, one external patent connector with query approval, the assessment record with final approval and re-approval after change, access control, an append-only audit log, report export and a decision log without retraining [DEC-028]. Grouping of the whole stored collection, generated summaries and mandatory labelling of every displayed candidate are outside the funded scope. The constraint that the design allow later extension [C1] is met by four defined interfaces: the import format, the retrieval interface, the connector interface and the platform adapter, the last of which is specified but not implemented [IF-01, IF-02, IF-03, IF-07]. The prototype is designed to support alignment with ISO/IEC 27001 and ISO/IEC 20000-1 through role-based access, audit logging, versioned components and a risk assessment of its data flows; it is not certified, and no conformity is claimed [C2, CLM-043, ISS-010]. Assessor decisions are logged in a reusable format, and no component learns from them [C3, AD-10].

### Research sources, tools and test design

Methods are taken from peer-reviewed retrieval and evaluation literature and from official model, library and service documentation logged in the project's source register; licences and input limits of the candidate models were read on their official model pages [SRC-033, SRC-037, SRC-075 to SRC-077]. The project uses no physical modelling or simulation tools. Its models are executable specifications: the record state model is written as a transition table from which the approval tests are generated, and the evaluation protocol is implemented as scripts that recompute every reported figure from stored judgment and run files.

Every retrieval result is tied to one of two data tracks that are never pooled. Track S uses sponsor data, judged by sponsor assessors where they can take part, and runs only if the sponsor releases data [ISS-002, ISS-003]. Track P uses public or constructed substitute data and project judges. Test sets are split by submission date: thresholds and fusion weights are tuned on an earlier development segment, and each configuration is run once on the later test segment, after the protocol has been frozen. A comparison is reported as non-inferior, superior, non-inferiority not established, inferior or below floor, and the prototype is not required to be better than the BM25 baseline [ISS-045].

### 1. Prototype design specification and data-protection baseline [WP1]

This activity fixes, in one design specification, everything the build activities implement, so that activities 3 to 5 can be accepted against a written reference rather than against each other. The field map and import-file specification are derived from the sponsor's export schema if it is released and otherwise from the substitute schema; the minimum fields are a platform identifier, title, body text and submission date, plus source type, availability status and permission note for items from a solution-example source [T1.1, IF-01, ISS-008]. The assessment template is a configuration file of fields, outcome codes and mandatory items. If the sponsor supplies no assessment content, a placeholder template is used and labelled as such [AD-07, ISS-005].

The record state model is written as a transition table with one row per allowed combination of state (Draft, In review, Submitted, Approved, Returned), event and role, and a default of rejection for every combination not listed [T1.2]. Two properties are stated separately from the table so that they can be checked against it rather than derived from it: no transition into Approved exists except the approval event performed by an authenticated user in the assessor role [CP-5], and any edit to an approved record creates a new Draft version [CP-6]. The optional second approver is a setting, off by default [AD-06, ISS-034]. The interfaces for retrieval, connectors, the record, report export, decision-log export and identity are specified with request and response schemas; the platform adapter is specified only [T1.3, IF-02 to IF-08].

The information security risk assessment walks each data flow and trust boundary in the architecture [DF-01 to DF-08] and records, for each, the data that crosses it, the threats of disclosure, unauthorized change, unauthorized state transition, loss of availability and unattributable action, the treatment chosen and the decision left to the sponsor [T1.4]. The external-query flow records the query-approval control [CP-1]. The same task produces the role and permission matrix for the three project roles (assessor, administrator, evaluator) and a retention and deletion procedure for imported data, test collections and cached external results, with deletion at project close as the default until the sponsor decides otherwise [AS-05, ISS-035, ISS-036]. The reference environment is specified by hardware class, operating system and runtime versions, and the components of the tool table are pinned to exact versions, with each licence file read on the pinned version [T1.5, ISS-041].

Acceptance is by a design review against a checklist: every function in scope maps to a component, an interface and a test, the transition table enumerates every state, event and role used by the approval tests, and every open owner input is listed with the default applied [T1.6, D1.1 to D1.3, M1]. The main risk is that sponsor inputs on the export format, assessment content, approval model and accounts do not arrive [RSK-01, ISS-005, ISS-034, ISS-035]; the substitute schema and the defaults above keep the build moving, and changing them later is a configuration change, not a redesign. The specification also fixes the funded function set, so that an optional function can enter the build only through a recorded owner decision [RSK-14].

### 2. Evaluation protocol, test collections and evaluation harness [WP2]

The evaluation tooling is built and checked before any test pool is judged, because a protocol changed after test data has been seen cannot support a comparison [S05 rule 2]. The activity starts with the licence check of each substitute candidate on its original distribution [T2.1]. For the duplicate-question collection CQADupStack, the S07 check found no licence statement on the original distribution page, a script repository that points to an unread licence file of unstated scope, the CC BY-SA 3.0 licence that Stack Exchange stated for its community content at the time of the 2014 data dump, and two third-party mirrors with conflicting licence statements [SRC-079, SRC-082 to SRC-085, CLM-059]. The data licence is therefore not established, and the collection may not be used until four conditions are recorded: a data licence from the original distribution, compatibility with the planned evaluation use, consistency with the upstream licence, and an owner decision [ISS-044]. If the gate does not pass, another candidate that passes the same check is used, and the harness reproduction uses another benchmark with published reference runs and a licence that passes.

The protocol and judging guide fix the grade scales with worked examples, the configurations, the metrics (nDCG@10 for R1, P@5 at grade 2 or above for R2, success@10 for R4, with Recall@20, MRR, bpref and judged@10 as secondary and completeness measures), the planning values with their confirmation status, the significance procedure and the acceptance targets, and the protocol records its freeze date [T2.2, D2.1, M2]. It carries the four corrections made after the independent audit of the evaluation design. First, every confirmatory comparison is a non-inferiority test followed by a superiority test: non-inferiority is concluded only when the lower limit of the two-sided 95% paired bootstrap interval lies above minus a margin fixed in advance (0.05 for nDCG@10 and P@5; 0.10 for success@10; planning values awaiting confirmation), and a non-significant superiority test is never read as non-inferiority [SRC-087, ISS-042, ISS-049]. Second, the BM25 baseline is a reference that the selected configuration must not fall below by more than the margin, not one it is required to beat [ISS-045]. Third, absence of relevant items is stated at the level checked: the judged pool, a deeper sampled check, or exhaustive judging of a small source [ISS-043]. Fourth, the Holm step-down procedure controls the family-wise error rate across the confirmatory comparisons of each track [SRC-089].

Test collections are built per track with time-ordered development and test splits; each collection carries its source, licence note, track label, split dates and checksum, and a manifest script rejects any collection that mixes tracks [T2.3, D2.2]. If no solution-example source is confirmed and the owner approves it, an R2 substitute is constructed: project judges write need statements in the form of a submission, which are searched against a public solution-description source whose terms pass the licence check [T2.4, ISS-038]. Without it, the R2 target could not be tested on any data.

The harness reads run files in the standard six-column format, computes the metrics through the toolkit's evaluation functions and through project code for success@10 and judged@10, and implements the paired bootstrap, the sign-flip randomization test (including the margin-shifted version used for non-inferiority), the Holm adjustment and Clopper–Pearson intervals [T2.5, D2.3, SRC-090]. Metric code is unit-tested against hand-computed examples. A judging screen shows one query and one item at a time, in random order, without the name of the configuration that retrieved the item, and records the grade and the time taken. The harness is accepted when it reproduces a published BM25 reference run within rounding [T2.6, FT-01, ET-02]. A harness that cannot reproduce a published figure is not used for any comparison. The frozen protocol, the time-ordered split and the single test run guard against tuning leaking into the test results, and pooling every configuration, including the date-ordered list, limits the bias against configurations that retrieve unjudged items [RSK-09, RSK-12, RSK-13].

### 3. Ingestion and retrieval for similar submissions and solution examples [WP3]

The ingestion adapter parses delimited or JSON Lines files against the field map and writes an import report that lists accepted rows, rejected rows with the reason, and exact duplicates found by content hash [T3.1, D3.1, FN-01]. Each solution-example source is entered in a source registry with its source type, availability status and permission note, and every stored item inherits these fields so that they can be shown beside each result [MS-10]. The normalization pipeline cleans text, computes exact-copy hashes and word-shingle fingerprints for the near-duplicate baseline, stores a language tag and splits long texts into overlapping passages sized to the input limit of each encoder (256 word pieces for all-MiniLM-L6-v2, 512 tokens for multilingual-e5-base), counting how many passages each record produces so that truncation is visible per corpus [T3.2, SRC-012, RSK-10]. If submissions turn out not to be in English, the English-only encoder is dropped and the two multilingual encoders remain [ISS-007, AS-06].

For each registered corpus the index layer builds one lexical index over passages carrying their record's title, and one vector index per dense encoder over L2-normalized passage embeddings, and stores the index version with the record of every query [T3.3, D3.2, AD-11]. The retrieval service runs every configuration behind one interface: the date-ordered list, BM25 with parameters tuned on the development split, the fingerprint baseline, the three dense encoders without fine-tuning (no labelled training pairs exist), reciprocal rank fusion and convex score combination of BM25 with the best dense run, and optional cross-encoder re-ranking of the top 50 [T3.4, SRC-001, SRC-007, SRC-008, SRC-006]. A record's score is its highest passage score, and that passage is returned as the evidence span shown before the score [AD-05]. Each query for R1 searches only items dated before the submission; for vector search this is done by filtered search if the pinned Faiss version supports it and otherwise by over-fetching and filtering, with the number of candidates lost to filtering logged. Evaluation runs use exact vector search so that approximate-search error does not enter relevance comparisons; approximate search is introduced only where exact search cannot meet the response-time target, and its overlap with the exact top results is then reported [SRC-034, SRC-035].

The R1 display threshold and the R2 "no example above threshold" signal are set on the development split only, by a rule fixed in the protocol, and are not changed after the test run [T3.5, ET-01b, ET-04]. Before the configuration set is frozen, each corpus is encoded at the corpus sizes the owner confirms (10,000, 100,000 and 1,000,000 items are the planning brackets), and encoding, search and re-ranking times are measured on the reference environment; configurations that cannot meet the response-time target of 5 seconds at the 95th percentile (a planning value) are removed from the timing test [T3.6, D3.3, FT-02, PV-09, PV-10]. The memory arithmetic of 4 bytes per dimension per vector puts one million 1,024-dimensional vectors at about 4.1 GB before index overhead, which is where index compression or a smaller encoder may be needed [CLM-056]. Unit and integration tests cover parsing, validation, hashing, segmentation, index building, date filtering and the presence of an evidence span for every candidate [T3.7]. If the sponsor releases an export, it is parsed against the field map as a feasibility test [T3.8, FT-04].

The activity is accepted when every configuration that passed the timing check produces a run file on the development split, every candidate carries an evidence passage, and the import report lists rejected rows with reasons [D3.1 to D3.3]. The technical risks are submissions in a language the English encoder cannot handle [RSK-05], long texts that exceed encoder limits, made visible by the truncation counts [RSK-10], and reference hardware that cannot run the stronger configurations within the response-time target, addressed by the timing check before selection, the compact encoder and index compression [RSK-11]. Dense configurations may also bring no benefit over BM25 on submission-like text; the evaluation is designed to show that outcome, and the default-configuration rule in activity 6 handles it.

### 4. External prior-art retrieval with query approval [WP4]

The connector framework defines a plug-in contract for any external source: a query with an optional maximum number of results returns items with source name, external identifier, title, abstract text, date, link, terms note and retrieval time [T4.1, IF-03, AD-04]. The framework applies a rate limiter set below the service's stated limit (for EPO Open Patent Services, the fair-use guide value is ten searches per minute), retries with back-off on refusals, and caches every result in the content store with its provenance, so that a record can be reproduced if the external source changes [CLM-051]. One connector is built for the service the owner selects; EPO Open Patent Services is recommended because its registration route, free tier and terms permitting inclusion in the user's own products are documented, while key issuance for the PatentsView API is uncertain and the Lens terms were not read [T4.2, ISS-040, CLM-052, CLM-053]. A smoke test with public test queries checks authentication, parsing, provenance and the behaviour under rate limiting [FT-03, D4.2].

A candidate query is built from the submission's title and its highest-weighted passages by selecting terms with TF-IDF weights computed against the stored corpus, and translated into the service's query syntax by the connector [T4.3]. While external disclosure is not authorized, the assessor sees the exact text that would be sent, may shorten or redact it, and approves it; only approved text can reach the connector, and the approval, the approver and the exact text sent are written to the audit log [CP-1, DEC-028]. The control is enforced at two levels: the record service refuses to pass unapproved text, and the reference environment allows outbound connections only from the connector process to the configured service hosts, so that a bypass attempt from another component fails at the network level. The connector computes a hash of the request payload it sends and logs it beside the hash of the approved text; the disclosure test compares the two for every query [ET-08, MS-05].

If no patent service grants access, the assessor runs the search in the service's own interface and enters the results through a manual-entry form with the same provenance fields; the R4 evaluation is then marked as not run against a connected service [T4.4, AS-08, RSK-06]. Tests cover the connector contract, attempted bypasses of query approval through the interface, the service layer and direct network calls, and the completeness of provenance on every stored result [T4.5, D4.1]. A second patent connector is built only if the owner selects more than one service; it uses the same contract and tests [T4.6]. The R4 evaluation compares three formulations for each need statement: an unaided keyword query written by a judge who has not seen the automatic query, the automatic query, and the automatic query after a different judge has edited it at the approval step [ET-09]. Because the evaluation uses public need statements on Track P, it does not depend on the disclosure decision; if disclosure is never authorized, no Track S result exists for R4 and the report says so [ISS-033, RSK-07].

### 5. Assessment record, review interface and approval controls [WP5]

The record service is the only component that changes record state [T5.1, AC-09]. It loads the transition table from the design specification at start-up and rejects any request whose state, event and role combination is not in the table. The outcome field is writable only inside the approval transaction, and a database trigger rejects any other write to it, so that the rule holds even for code paths that bypass the service layer. Approval binds the record version to the authenticated assessor, and every approved record stores the versions of the models, indexes, connector and template used [CP-5, AD-11, MS-06]. An edit to an approved record creates a new Draft version that needs approval again [CP-6].

Access control uses project-managed accounts with salted password hashing and expiring sessions, and checks permissions on every call to the record interface [T5.2, AC-12, AS-05]. The audit log is an insert-only table: the application's database role has no update or delete permission on it, and each entry stores a hash of the previous entry, so that removal or alteration of an entry is detectable by recomputing the chain [T5.3, AC-13]. The record service, access control, audit log and exports form deliverable D5.1. The review screens show, for each listed item in the R1, R2 and R4 lists, the matching passage first, then the source type, availability status and terms note, and only then the score [T5.4, AC-10, AD-05, MS-10]. The query-approval screen, the assessment template form and the approve and return actions are shown only to the assessor role, and scripted browser tests check both the display order and the role restriction [D5.2]. Approved records are exported as a human-readable report and as a machine-readable file validated against the schema in the design specification, and the decision log is exported with submission identifier, candidate identifier, corpus, label, reason, assessor role and time, without names; no component retrains on it [T5.5, IF-05, IF-06, AD-10].

The approval-enforcement test suite is generated from the transition table: it attempts every combination of state, event and role (including the evaluator and administrator roles and unauthenticated requests) through the interface and directly against the service layer, adds expired sessions and replayed requests, and runs randomized event sequences produced by a property-based test generator [T5.6, D5.3, ET-06]. The test oracle is the pair of properties stated in activity 1, checked on the database after every step, not the transition table itself, so that an error in the table is caught rather than reproduced. The re-approval test changes each editable field of an approved record once and checks that a new version requiring approval is created; it also recomputes the audit-log hash chain [ET-07]. The pass criterion is zero records reaching Approved without an approval event and zero changes escaping re-approval [MS-04]. Coverage is reported against the transition table. The approval model is still open: if the sponsor requires a second approver or other approving roles, the setting and the transition table change, and the generated suite follows them without new test code [ISS-034]. The optional review controls for per-candidate labelling, summaries and grouping are not built [RSK-14].

### 6. Prototype integration and evaluation [WP6]

The outputs of activities 3 to 5 are integrated into one release built from tagged sources by deployment scripts on a clean instance of the reference environment; the release is accepted when all their test suites pass on it [T6.1, D6.1, M3]. Pilot judging follows on the development queries: it measures agreement between judges (Krippendorff's alpha on the ordinal scale, Cohen's kappa on the binary split) and time per judgment, allows one revision of the judging guide, and collapses the R1 and R2 scales to three levels if alpha stays below 0.67 after the revision [T6.2, FT-05, ET-11, SRC-069, SRC-027, PV-05]. The pilot also supplies the variance and discordance estimates for the sample-size checks: the standard deviation of per-query differences against BM25 for R1 and R2, and the share of discordant need statements on ten R4 development statements per track. If the planned 60 test queries cannot give a 95% interval whose half-width is no larger than the margin, the query count is raised within the judging budget or the result is reported as underpowered; for R4, the owner records before the test run whether to raise the number of need statements, accept an estimate without a non-inferiority claim, or revise the margin with a written reason [ISS-049]. With 30 need statements, a non-inferiority margin of 0.10 is unlikely to be met even if the two query types perform equally, so this decision is expected rather than exceptional. Absolute floors are fixed and dated before the test run [PV-11].

Configuration selection uses the development split only and is recorded with its reasons [T6.4, D6.2]. Test pools are then judged blind to configuration, with 20% of query-item pairs judged by two judges and disagreements adjudicated by a third [T6.3, PV-04]. For a random sample of ten test queries per test and track whose pool contains no relevant item, items ranked 11 to 50 by every configuration are judged as well, or the whole source if it holds no more than 200 items dated before the query [ET-12, PV-14, PV-15]. The test split is run once per configuration; the approval, re-approval, disclosure, attribution and response-time tests are run on the release [T6.5, ET-05 to ET-08, ET-10, D6.3].

The evaluation report states every result with its data track, confidence interval, Holm-adjusted p-value and outcome label, never combines Track S and Track P, and reports a difference whose interval includes zero as "no supported difference" [T6.6, D6.4, M4]. It reports the "no example found" error rate as a lower bound measured against the judged pool, beside the estimate from the deeper check. If on a track the selected configuration is not shown to be non-inferior to BM25, or falls below its floor, the report says so and the as-built specification makes BM25 the default configuration for that kind of corpus. The configuration comparisons are repeated with each judge's own grades on the double-judged subset to check whether the ranking of configurations is stable [SRC-026]. The main risks of this activity are short judging time, low agreement and test sets too small to separate configurations; they are handled by project judges working from the same guide, the scale-collapse rule and the sample-size checks above [RSK-03, RSK-04, RSK-08]. If sponsor assessors can take part, a structured walk-through of the review screens records how they use them; the evaluation does not depend on it [T6.7, ISS-012].

### 7. Technical documentation and handover [WP7]

The design specification is updated to the built prototype and accompanied by deployment and operation instructions for the reference environment; the instructions are accepted when a person not involved in the build deploys the release from them and the rehearsal is recorded [T7.1, D7.1]. Who that person is will be decided with the team composition, which is not yet settled [ISS-051]. The information security risk assessment is updated to the built system, and imported data, test collections and cached external results are deleted as the retention procedure specifies, with a deletion record [T7.2, D7.2, ISS-036]. The source code and configuration are packaged with an inventory that lists every third-party component and model with its version, licence and training-data terms; a scan confirms that no sponsor data is in the package [T7.3, D7.3, ISS-041]. A handover demonstration on the release shows the R1, R2 and R4 lists and the approval and re-approval workflow, and acceptance or listed reservations are recorded [T7.4, D7.4, M5]. Continuity notes for later stages describe the decision-log format, the platform adapter specification and the limits found in evaluation [T7.5].

### Limits of the method

The evaluation measures retrieval quality on judged test sets and the conformance of the workflow to the approval rules. It does not measure assessment speed, assessor workload or decision accuracy in live use, because no baseline review time or error rate exists [ISS-011]; the benefits expected in the requirements statement remain hypotheses for a later timed study [CLM-006]. Results on substitute data describe the methods on that data and do not predict results on sponsor submissions.
